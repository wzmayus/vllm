**Analysis Confirmation: What is consuming VRAM?**

Based on the logs and code analysis, **BOTH the Weights and the KV Cache are currently allocated on GPU VRAM**, causing the 29GB usage.

1. **Weights (\~15.27 GB)**:

   * `load_model` uses the standard PyTorch allocator, which loads weights directly to GPU VRAM. The `Aliased Init` logic currently fails to intercept this.
2. **KV Cache (\~13.7 GB)**:

   * In `initialize_from_config`, the `initialize_kv_cache` call is **not wrapped** in the `VMMAllocator` context manager for `Aliased Init` mode (unlike Sleep Mode).

   * Therefore, it uses the default PyTorch allocator, ignoring our `sparse_limit`, and allocates full physical VRAM for the cache blocks.

**Solution Plan**

1. **Fix KV Cache Allocation**:

   * Modify `gpu_worker.py` to ensure `initialize_kv_cache` is wrapped in `VMMAllocator.use_memory_pool("kv_cache")` when `aliased_init` is enabled. This will enforce the sparse limit (allocating VA only, backed by minimal Host memory).

2. **Fix Weight Allocation**:

   * **Modify** **`csrc/cumem_allocator.cpp`**: Expose `make_tensor_from_ptr` to allow creating PyTorch tensors from raw VMM pointers with a custom deleter.

   * **Modify** **`vllm/device_allocator/vmm_allocator.py`**: Add `allocate_tensor` helper.

   * **Modify** **`gpu_worker.py`**:

     * Update `load_model` to temporarily force loading to **CPU**.

     * Implement `alias_model_weights` to move these CPU weights into Host-Backed VMM memory.

     * Replace model parameters with these new VMM-backed tensors.

3. **Verification**:

   * After these fixes, startup VRAM usage should drop to near zero (< 2GB overhead).

   * Activation will then trigger the move to GPU.
